## Plan: Polaris UI/UX Complete Revamp

Polaris has a solid dark-mode aesthetic and a functional MVP, but suffers from poor mobile UX, no onboarding, scattered activity logging flows, missing data visualizations, and no offline/PWA support. This plan restructures the UI around a **mobile-first, gesture-friendly, progressive-disclosure design** across 8 workstreams, requiring **no backend changes** (the API already supports everything).

---

### Critical Problems Found

| # | Problem | Impact |
|---|---------|--------|
| P1 | **No onboarding flow** — new users land on empty dashboard | Users don't know what to do → abandon |
| P2 | **Mobile UX is an afterthought** — hamburger nav, no touch gestures, no bottom tab bar | Unusable as daily phone driver |
| P3 | **3 overlapping log forms** (`QuickLogBar`, `QuickLogModal`, `LogActivityForm`) | Confusing, redundant, hard to maintain |
| P4 | **No data visualization** beyond a basic heatmap and progress bars | Can't see trends or patterns over time |
| P5 | **No calendar/week view** — designed in docs, never built | Can't plan ahead or review past days |
| P6 | **No global search** — only in-page client-side filters | Finding old activities/goals is tedious |
| P7 | **No settings/preferences page** | No customization, no data export UI |
| P8 | **No offline/PWA** — no service worker, no manifest | No app-like feel, no installability |
| P9 | **No skeleton loading** — shimmer CSS exists but is unused | Jarring loading jumps |
| P10 | **Goal hierarchy invisible** — `parentId` exists in DB but no tree view | Sub-goals not discoverable |
| P11 | **No keyboard shortcuts** | Power users have no fast paths |
| P12 | **No meaningful animations** | App feels static and lifeless |
| P13 | **Category (growth/maintenance) invisible** | Feature exists in data model but never shown |
| P14 | **Streak display is a plain number** — no celebration, no emotional reward | No dopamine for consistency |

### Decisions
- **Keep dark theme only** — Polaris Celestial is the brand; no light mode now
- **No new backend endpoints needed** — the existing API already exposes everything
- **Recharts over D3** — simpler, React-native, sufficient for these charts
- **CSS-first animations** — avoid framer-motion bundle bloat unless spring physics needed for swipe
- **Radix headless primitives** recommended for Sheet, Dialog, Tooltip — they handle accessibility correctly while preserving custom styling
- **No drag-and-drop library initially** — use native HTML5 DnD for week view; add `dnd-kit` only if needed
- **Growth/maintenance auto-detection** — if activity has a linked goal → growth; no goal → maintenance (don't force users to choose)

### Further Considerations
1. **Should we adopt Radix UI headless primitives for accessible Sheet/Dialog/Tooltip?** Recommendation: Yes — they solve accessibility for free while we keep full style control. This would be a new dependency.
2. **Should Week View support drag-and-drop on mobile?** Recommendation: No — use long-press → move modal instead. Touch DnD is unreliable cross-browser.
3. **Should we add a notification/reminder system?** Recommendation: Defer — browser notification API is limited; more valuable as a PWA push notification in a later phase.
